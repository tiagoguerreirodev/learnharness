# Desktop builds and releases

This is a maintainer reference. For installation and normal use, start with [Getting started](getting-started.md).

## Platforms and prerequisites

CI/release uses **Node 26**. **Desktop release builds only Windows x64** on `windows-2025`: an unsigned, per-user NSIS installer. Windows may show SmartScreen/unknown-publisher warnings; signing and update-signature policy are unchanged.

Local packaging still supports macOS arm64 (signed/notarized DMG + updater ZIP) and Linux x64 (AppImage + `.deb`). AppImage is the primary Linux download; `.deb` updates may require an administrator password. Build **on the target OS**: Next traces native binaries for its build machine, so a macOS standalone tree is not a Windows/Linux payload.

Builder auto-discovers [`electron-builder.cjs`](../electron-builder.cjs), which composes [`electron-builder.base.yml`](../electron-builder.base.yml) with exactly one resolved GitHub destination using `releaseType: draft`. The renamed YAML base is not auto-discovered and must not define `publish` at any level or extend another configuration. Keep the adapter as the default entry point; do not bypass it with the base as `--config`, add competing `package.json.build` configuration, or import private Builder internals. Production composition uses Node, the existing YAML dependency, and the shared resolver; verification uses Builder's public `Packager` API to inspect the effective default configuration.

macOS icon compilation requires **macOS 26+ and Xcode 26+** for `build/icon.icon`. `actool` creates `Assets.car`; `after-pack.cjs` restores the full-resolution fallback icns. Windows/Linux use flat-design icons generated by `scripts/make-icons.mjs`. Linux desktop identity is `learnharness.desktop`.

The custom app bar remains on all platforms. macOS has left traffic lights/system menu; Windows/Linux use right-side native Window Controls Overlay and reveal the native menu with Alt.

## Build-time release repository

The shared [resolver](../scripts/release-repository.cjs) selects the first applicable source:

1. Explicit process environment `LH_RELEASE_REPOSITORY=owner/repo`.
2. `GITHUB_REPOSITORY=owner/repo` (normally supplied by GitHub Actions).
3. The **application project's** local Git `origin`.
4. Failure for desktop packaging, including `--publish never`.

A defined but empty or malformed higher-priority input is an error, not permission to fall through. Unset an override to return to automatic detection. Standard GitHub origins such as `https://github.com/your-org/your-fork.git`, `git@github.com:your-org/your-fork.git`, and `ssh://git@github.com/your-org/your-fork.git` work. Linked worktrees work, including worktree-specific origin configuration. An archive without its own Git metadata cannot inherit an enclosing unrelated checkout's origin. Homepage, attribution, and an `upstream` remote are **not** fallbacks.

Only canonical lowercase public metadata leaves the resolver: owner/repository and `https://github.com/owner/repo`. Renderer build metadata exposes `LH_RELEASE_REPOSITORY_URL` as an **output**, not another override. Settings uses its `/releases` page without assuming any tag. Homepage, author attribution, and provider identification remain separate and unchanged. No token or credential-bearing origin is needed in a shipped application; never embed credentials.

Web-only builds with unavailable identity succeed and omit Release notes. Invalid supplied identity still fails. This optional web behavior does not weaken strict desktop packaging.

**Use the same identity throughout the production build, standalone curation, packaging, and verification.** Export an override in the shell, not just on the Builder command. Do not rely on Next-only `.env.local` loading to configure Builder. When identity changes, rebuild the renderer, re-curate standalone output, and re-package; frozen `.next` output from another repository cannot be reused. Changing an environment variable in an installed app does not redirect its baked updater or renderer link.

For an existing application checkout or linked worktree, automatic detection can be inspected without building or publishing (Bash, from the application root):

```sh
unset LH_RELEASE_REPOSITORY GITHUB_REPOSITORY
node -e 'console.log(require("./scripts/release-repository.cjs").resolveReleaseRepository())'
```

For example, an SSH origin `git@github.com:your-org/your-fork.git` resolves to `{ owner: 'your-org', repo: 'your-fork', url: 'https://github.com/your-org/your-fork' }`. An unidentified archive instead fails with instructions to set `LH_RELEASE_REPOSITORY=owner/repo`.

## Build pipeline

Run from the application root on the target OS. Environment-prefix/export examples below require a POSIX shell, such as Git Bash on Windows; the Windows release job uses Bash.

1. `npm ci`
2. `npm run plugins:setup` — generate ignored SDKs and install locked source-plugin dependencies.
3. Run native renderer/browser-service tests in Electron's Node:
   ```sh
   ELECTRON_RUN_AS_NODE=1 NODE_ENV=test npx electron --import tsx --test tests/pdf-native-render.test.ts tests/pdf-ops.test.ts tests/svg-native-render.test.ts tests/browser-service.test.ts
   ```
4. `npm run build`
5. `node scripts/smoke-provider-runtime.mjs` — check the **fresh trace before curation**, including native provider initialization and fixture payloads, not real sign-in/generation.
6. `node scripts/build-server.mjs` — copy static assets, validate prompt assets, refuse known data/credential leaks, and remove only standalone-root old installers/development Electron.
7. `node scripts/smoke-server.mjs --electron` — check renderer/demo dependencies, providers, gzip backpressure, and isolated standalone HTTP boot under Electron's Node.
8. Package and verify using the appropriate local/release policy below.

The shell/updater ships in `app.asar`; the server/native renderers ship unpacked as `extraResources`. Pi/PDF/canvas/resvg/Photon dynamic assets are explicitly traced in [`next.config.ts`](../next.config.ts). Keep trace exclusions narrow: broad `dist/**` or `data/**` patterns can remove dependency assets. Curation guards are not a substitute for inspecting a changed payload.

The release workflow also checks providers from the **packaged** payload under host Node and packaged Electron, then exercises the demo helper using the app's Electron, without a system-Chrome fallback. HTTP boot or catalog output alone does not test these lazy paths.

`smoke-image-runtime.mjs` separately checks synthetic Photon in-process/worker resizing in standalone output. It accepts `--standalone <dir>` and `--runtime <binary>`; it is **not currently invoked by CI/release workflows**.

### Windows source-archive or explicit-override example

Extract the application source archive, open Git Bash in its root, and replace `your-org/your-fork` with the intended GitHub release repository. This complete nonpublishing sequence also works in a checkout when deliberately overriding origin/Actions detection:

```sh
set -euo pipefail
export LH_RELEASE_REPOSITORY=your-org/your-fork
export NEXT_TELEMETRY_DISABLED=1
npm ci
npm run plugins:setup
npm run typecheck
npm run lint
ELECTRON_RUN_AS_NODE=1 NODE_ENV=test npx electron --import tsx --test tests/pdf-native-render.test.ts tests/pdf-ops.test.ts tests/svg-native-render.test.ts tests/browser-service.test.ts
npm run build
node scripts/smoke-provider-runtime.mjs
node scripts/build-server.mjs
node scripts/smoke-server.mjs --electron
npx electron-builder --win --x64 --publish never
npx tsx scripts/verify-release.ts package dist
node scripts/smoke-provider-runtime.mjs --standalone dist/win-unpacked/resources/server/standalone
node scripts/smoke-provider-runtime.mjs --standalone dist/win-unpacked/resources/server/standalone --runtime dist/win-unpacked/LearnHarness.exe
node scripts/smoke-demo-runtime.mjs --standalone dist/win-unpacked/resources/server/standalone --runtime dist/win-unpacked/LearnHarness.exe --browser
```

The exported override remains present for **both** `npm run build` and Builder, as well as verification. Inspect the packaged Settings Release notes destination separately: it must be `https://github.com/your-org/your-fork/releases`. The output gate does not inspect renderer links. Do not install an update or publish a release merely to inspect these outputs.

### Other local packages

`npm run desktop:dist` is the local **signed macOS** path using the `LH_NOTARY` keychain profile and Xcode `DEVELOPER_DIR`. It clears `dist` and `.next/standalone`, builds, checks the fresh provider trace, curates, runs the server smoke under **host Node**, and packages. It does not itself run the Electron-Node/post-package gates or the tag-upload workflow. Export any repository override before invoking it.

For Linux, perform build steps 1–7 on Linux with the chosen identity, then `npx electron-builder --linux --x64 --publish never`. The Windows output gate below is not a Linux/macOS verifier. Local cross-platform targets do not imply release jobs for those platforms.

## CI and release modes

[CI](../.github/workflows/ci.yml) runs typecheck/tests/lint on Ubuntu, plus standalone/native checks on macOS, Windows, and Linux. Its `macos-15` job does not compile the release icon.

[Desktop release](../.github/workflows/release.yml) first resolves and validates identity in the quality job, then passes canonical `owner/repo` to the Windows production build, Builder, and verification. Set the optional **repository Actions configuration variable** `vars.LH_RELEASE_REPOSITORY` for an explicit override. A nonempty value becomes `LH_RELEASE_REPOSITORY`; an absent/empty Actions variable means automatic detection, not a defined empty process override. This is not a secret or a workflow-dispatch input; dispatch remains input-free.

- **Manual dispatch:** artifact-only unsigned Windows installers retained for seven days as `learnharness-windows-x64`. No release creation, upload to a release, or publication; draft verification is skipped. This remains true even when manually selecting a tag ref. A deliberate cross-repository override is permitted for this nonpublishing rehearsal.
- **Tag push matching `v<package.json version>`:** quality gates, one draft-preparation job, Windows packaging/upload, then read-only draft verification. A selected repository differing from the running `GITHUB_REPOSITORY` fails **before any draft/release mutation**. Release APIs stay bound to the workflow repository; the override never redirects them. Published/ambiguous existing releases fail preparation; a single draft is reused, and same-ref runs serialize rather than cancelling uploads. **The workflow never publishes the draft.**

Current Windows packaging is unsigned in both modes; no Apple signing/notarization secrets are used by this workflow. The built-in `GITHUB_TOKEN` supplies scoped `GH_TOKEN` only where release operations need it, not the production renderer build. Never commit keys, certificates, passwords, or environment-secret files.

### Strict Windows output gate (both modes)

```sh
npx tsx scripts/verify-release.ts package dist
```

This offline, tag-free command loads the **actual effective default Builder configuration** and requires exactly one matching public GitHub draft destination, without alternate destinations, nested publish overrides, host/private/token fields, or naming/target drift. It then checks:

- `dist/win-unpacked/resources/app-update.yml` contains the same public destination and only allowed updater fields.
- The expected installer, blockmap, and `latest.yml` are regular, nonempty files.
- Feed version, exact installer reference, bare filenames, actual size, and legacy path/hash fields agree; URLs/traversal and inconsistent entries fail.
- The actual installer's SHA-512 matches the feed.

The workflow runs this after Builder in **both modes**, before packaged runtime smokes and artifact retention. Failure means **do not publish**. The gate does not decode blockmaps, install an update, prove signing/channel eligibility, or validate the renderer link.

### Draft verification (tag pushes only)

[`scripts/verify-release.ts`](../scripts/verify-release.ts) additionally requires one draft matched by `v<version>` or bare `<version>`, refusing zero/two matches or a published match. Bare-version matches warn because later runs could split assets across tags; the triggering tag must still be `v<package.json version>`.

The draft must contain **exactly three uploaded, nonempty assets**, also retained together in the Windows Actions artifact:

| Assets | Purpose |
| --- | --- |
| `LearnHarness-<version>-x64-setup.exe` | Windows installer/updater |
| `LearnHarness-<version>-x64-setup.exe.blockmap` | Differential-update metadata |
| `latest.yml` | Windows updater feed |

Feed versions, exact referenced asset sets, bare filenames, sizes, and legacy path/hash fields must agree. Missing/stale extra assets, path traversal/URLs, or Builder naming drift fail validation. Unlike the local package gate, remote verification does not download/hash the installer; it checks release asset metadata and the downloaded feed.

The verification job needs `contents: write` to list private drafts but performs GET-only operations. Its token is exposed only to release listing/feed download, not dependency installation or offline validation.

## Release runbook

1. Agree scope/version and complete relevant gates and human functional acceptance. Use manual dispatch for a safe Windows artifact-only rehearsal; check the selected repository and all three outputs, plus the packaged Release notes link.
2. For an explicitly authorized release, update package/lockfile versions, check the intended source on main, and push the matching tag. Clear any cross-repository Actions override first; it is permitted only for manual artifact-only runs.
3. Wait for **Windows packaging and Verify draft release**. Inspect the single draft's tag, notes, three assets, and feed. Diagnose failures before retrying. Re-upload replaces same-named assets; stale extras still fail. Deleting assets/releases is a mutation, not verification.
4. If editing draft metadata, include canonical **`tag_name: "v<version>"` in every metadata PATCH**, even for title/body changes; omission has reset tags before. Re-read tag, draft status, and assets afterward. A tag correction does not authorize deleting/recreating a release.
5. The owner checks the packaged build as needed and explicitly publishes the complete draft. Confirm public installers/feeds and applicable website links; use a prior installed version for separately authorized real update-path checks.

Shell, native-module, packaging/updater, or Electron changes warrant focused platform checks: install/open, window controls/dragging/zoom, setup/resume, PDF/SVG, and demo helper. Fixture gates do not prove account functionality or lesson quality. Do not repeat accepted feature testing without a concrete risk.

## Updates and website notification

Packaged apps check at startup and every 24 hours by default, download automatically, and install on quit or Restart. **Settings → General** provides release notes, manual checks, status, and Automatic updates. Manual and automatic checks use the same baked repository. Disabling automatic checks does not cancel downloads/staged installs; manual checks still download updates. Dev builds disable the updater. Errors go to `userData/logs/main.log`; `LH_UPDATE_FEED` remains a test-only generic-feed override.

Repository routing changes **no** update preferences, scheduling, version comparison, downgrade, or channel policy. The published prerelease `0.6.1-fast-mode` contains application version `0.6.1`: redirecting checks alone makes it neither eligible for stable-only checks nor newer than an installed `0.6.1`. Release notes uses `/releases`, so custom tags need no link convention, but automatic tag publication still requires `v<version>`. Already-shipped binaries keep their baked destination until rebuilt and reinstalled. Anonymous checks still require accessible, published release metadata and appropriate assets; private-release authentication is not added.

Sources: [`electron/main.cjs`](../electron/main.cjs), [`preload.cjs`](../electron/preload.cjs), [`update-settings.tsx`](../components/settings/update-settings.tsx).

For the upstream repository only, after stable publication, [`notify-website.yml`](../.github/workflows/notify-website.yml) dispatches the tag to the website using `WEBSITE_DISPATCH_TOKEN`. Forks are skipped by its repository guard; drafts/prereleases do not trigger it. HTTP 204 means the website update was queued, not deployed or publicly verified.
